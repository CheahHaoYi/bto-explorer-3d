# Develop

Turn the team's corrected project Page into a plan and a prototype they can try. Support software, games, installations, art, and participatory experiences. Preserve creative intent and the chosen medium. A successful prototype check is not a claim that the experience has been validated by participants.

## Read the current brief

First read `PROJECT-KNOWLEDGE.md` in the active project root, creating it if missing. Recover the Page and prototype locations from it. Use the Page explicitly linked or selected for this project; if no Page can be identified from the file or conversation, ask for its link before building. If several Pages are plausible, resolve the choice rather than creating a new PRD.

Read its latest content and applicable instructions through active Pages tools. Treat participant edits as current truth. Inspect the existing project files and relevant workspace instructions when present. Do not restart Start, repeat the persona interview, or overwrite the Page from chat memory.

An explicit request to Develop from this Page authorizes planning and reversible local prototype work. Resolve only material gaps or contradictions that prevent a fitting build. If scope clearly exceeds the remaining hackathon time, explain the issue and suggest a smaller version; use prioritization only if needed. Do not quietly discard part of the idea.

## Plan for the medium and deadline

Identify what kind of prototype can make this experience tangible. Use software only when it serves the medium. An installation may need a spatial mockup, a simulation of its behavior, materials instructions, or a facilitation rehearsal; explain what the agent can create and what the team must physically do.

Ask about remaining time, devices, equipment, team capacity, or required services only when the answer would change the build. Prefer an existing working setup or a small, dependable set of tools. Choose a stack that fits the interaction and delivery environment; explain the choice in a sentence the team can understand. Do not add logins, databases, AI features, analytics, or deployment solely because these are common app features.

Propose a short plan: the core experience, a few build steps, the prototype format, relevant dependencies, and any deliberate simulations. Distinguish facts from estimates. Keep research focused on resolving concrete implementation needs.

For apps, websites, and webapps, use the brief's confirmed Primary user flows and competitor reference links as the basis for the core experience. Do not repeat Start's Mobbin research or treat provisional flows as agreed. Resolve material flow changes with the team and record them in the same brief.

Write the plan in the same Page, preserving its strategy and PRD. If the plan makes a material creative or scope choice, get that choice confirmed before the dependent build. Otherwise, continue without an extra approval gate for ordinary implementation details.

## Build the greybox

Create the smallest coherent version of the agreed experience. Keep visuals simple enough that the team can focus on behavior, while making labels, controls, and feedback understandable. Basic accessibility and legibility belong here.

For digital projects, produce something runnable or interactive when feasible, rather than only describing screens. Use honest sample data or mocked dependencies where that saves time; distinguish them clearly from live behavior. For other media, create an appropriate spatial, temporal, or participatory mockup and a usable walkthrough.

If subagents are available and genuinely helpful, delegate independent build tasks with bounded ownership and a shared brief. Retain one lead agent for architecture, Page decisions, integration, and participant communication. Avoid concurrent edits to the same files or Page sections. Use a single agent when coordination would cost more than it saves.

Verify the core behavior with checks appropriate to the prototype. Open or present the actual result when supported. State what runs, what is simulated, what has been checked, and any material limitation. Do not require production infrastructure to demonstrate a hackathon idea.

## Try and refine the experience

Give the participant a direct way to open, run, or rehearse the prototype and a short walkthrough based on their intended experience. Ask them to try it and describe what works, what feels wrong, and what they would change. This is the experience-review checkpoint; do not mark it passed before their feedback.

Implement agreed changes and let them try again. Keep the loop small and focused on the experience. The team's feedback governs readiness; do not silently equate successful code checks with their approval.

Record the actual prototype link or location, working behavior, simulations, feedback, and decisions in the Page's Build and experience review section and `PROJECT-KNOWLEDGE.md`. Maintain the knowledge base throughout the build, not only at the end: capture actual technologies, AI models/tools and their uses, external assets/resources, experiments, learnings, team contributions when known, and agreed next ideas. Distinguish planned, implemented, and tested capabilities so Submit cannot mistake the PRD for a finished build. Update Workshop progress. Read the current Page before changes, follow active edit guards and guidance, and verify saves. Pages is the shared document; the knowledge base is its local context companion.

When the team says the experience works for them, offer the Design handoff with the same Page link and prototype location. Do not begin mood-board exploration automatically. Publishing, spending money, creating accounts, or changing Page sharing requires the relevant authorization.

If Pages is unavailable, explain the specific blocker and do not claim the plan or feedback has been saved to the Page. Preserve prototype work, maintain the local knowledge base with pending Page updates, and resume the shared-document updates once access works.
